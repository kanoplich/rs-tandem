По-этому предстояла возможность потренировать навык разбора чужого кода. `FormProvider` на момент ревью для меня был просто страшным словом, о котором я ничего не знал.

Упор был сделан на разбор `features/auth/ui/login-form.tsx` с дочерними компонентами в этой же папке, так как со схемой валидации при помощи `zod` я уже был знаком и она у меня самого уже была реализована.

Оказалось: `FormProvider` (из _React Hook Form_) — это React-контекст. Он позволяет «раздать» все методы формы всем вложенным компонентам без необходимости передавать их через пропсы, при этом файл формы становится чистым и читаемым:

```react
<FormProvider {...form}>
  {/* Провайдер "раздает" контекст всем детям внутри тега form */}
  <form className="space-y-6" onSubmit={form.handleSubmit(onSubmit)} noValidate>
    {/*Далее идут декомпозированные компоненты. Мы НЕ передаем им никаких пропсов.
         Они сами возьмут всё нужное из контекста (через useFormContext). */}
    <LoginEmailField />
    <LoginPasswordField />
    <LoginSubmitButton />
  </form>
</FormProvider>
```

Т.е. мы "оборачиваем" форму в `FormProvider` и передаем туда все методы через деструктуризацию `...form`. Это позволяет любому дочернему компоненту внутри получить доступ к форме.

А `noValidate` отключает браузерную валидацию, так как мы используем Zod, в моей форме этого не было:

```react
  <form onSubmit={form.handleSubmit(handleSubmit)} className="space-y-6">
```

Теперь разбор дочернего компонента на примере `LoginEmailField`:

Здесь происходит самое важное — то, как именно компонент получает доступ к данным формы:

```react
// Вместо использования хука useForm, мы берем useFormContext
const { register, formState: { errors } } = useFormContext<LoginFormValues>();
```

Вместо того чтобы принимать `register` и `errors` как пропсы, мы "вытаскиваем" их из контекста. Указываем `<LoginFormValues>`, чтобы TypeScript подсказывал нам поля.

**Как это работает:** `useFormContext` находит ближайший `FormProvider` выше по дереву и забирает оттуда методы.

Ну и регистрируем поле в `React Hook Form`:

```react
      <Input
        id="email"
        type="email"
        autoComplete="email"
        placeholder={AUTH_LOGIN_TEXT.EMAIL_PLACEHOLDER}
        className="focus-visible:ring-primary focus-visible:border-primary"
           /* Регистрируем поле в React Hook Form: */
        {...register('email')}
      />
```

Ну и последнее: правильный рендер ошибок:

```react
// Рендер ошибки с условием
{errors.email && <p className="text-xs text-destructive">{errors.email.message}</p>}
```

Т.е. конструкция `{errors.email && <p ...>}` - это **логическое «И» (short-circuit evaluation)**. Сначала проверяем, есть ли ошибка в объекте errors для поля `email`:

- Если `errors.email` существует (true), то отрисовывается тег `<p>`.
- Если `errors.email` (ошибки нет) равно `undefined`, то React просто проигнорирует правую часть выражения и ничего не отрендерит в DOM и пустой тег `<p>` не будет создан, и лишних отступов не будет.

Также Артур использует класс `text-destructive` (стандарт shadcn для красного цвета) и `text-xs` для размера. Класс `text-destructive` : в shadcn/ui этот класс обычно привязан к переменной CSS, которая отвечает за системный красный цвет. Использование этого класса вместо `text-red-500` — признак хорошего тона (если дизайн-система изменится, цвет ошибки поменяется везде автоматически).
