# Refactor Edge Functions: что было сделано и зачем

## Проблема: как было до рефакторинга

В проекте есть две Supabase Edge Functions, которые обращаются к LLM (AI-модели):

1. **chat-assistant** — чат-бот, который помогает студенту разобраться в задаче
2. **judge** — автоматический проверяющий, который оценивает ответ студента по рубрике

До рефакторинга каждая из этих функций **самостоятельно** делала HTTP-запросы к API языковой модели. Это создавало проблемы:

| Проблема              | Что происходило                                                                                    |
| --------------------- | -------------------------------------------------------------------------------------------------- |
| Дублирование кода     | Один и тот же код парсинга стрима скопирован в двух местах. Исправил баг в одном — забыл во втором |
| Привязка к провайдеру | Код жёстко привязан к Groq API. Хочешь сменить модель — переписывай оба файла                      |
| Нет обработки сбоев   | Если API вернул ошибку (лимит запросов, сервер лёг) — пользователь сразу видит ошибку              |
| Утечки на клиенте     | Пользователь закрывает чат, уходит со страницы с заданием, а запрос к AI всё ещё висит в фоне      |
| Потеря оценок         | AI мог перефразировать русские ключи рубрики, и оценка за критерий «терялась»                      |
| Нет логов             | Непонятно какая модель работает, сколько токенов тратится, есть ли проблемы                        |

---

## Решение: модуль `llm-client`

Создан **единый модуль** для работы с любым LLM API. Вместо дублированного кода — одна точка входа.

### Было vs Стало

**Было** (в каждой функции):

```typescript
const response = await fetch('https://api.groq.com/openai/v1/chat/completions', {
  method: 'POST',
  headers: {
    Authorization: `Bearer ${Deno.env.get('GROQ_API_KEY')}`,
    'Content-Type': 'application/json',
  },
  body: JSON.stringify({ model: 'llama-3.3-70b-versatile', messages, stream: true }),
});

// + SSE-парсинг
// + нет retry, нет timeout, нет fallback
```

**Стало** (одна строка):

```typescript
const client = getClient('chat');
const result = await client.chatStream({ messages, temperature: 0.4 });
```

Вся сложность спрятана внутри модуля.

## Архитектура модуля

```
supabase/functions/_shared/llm-client/
├── index.ts          — точка входа (getClient)
├── types.ts          — TypeScript-интерфейсы
├── config.ts         — чтение настроек из .env
├── llm-client.ts     — factory: создаёт нужный провайдер
├── retry.ts          — повторные попытки при сбоях
├── stream-utils.ts   — парсинг SSE-потока от AI
└── providers/
    ├── base.ts       — общая логика (наследование)
    ├── groq.ts       — провайдер Groq
    └── openrouter.ts — провайдер OpenRouter
```

### Паттерны, которые здесь используются

1. **Factory** — `getClient('chat')` сам решает какой провайдер создать, на основе `.env`
2. **Strategy** — провайдеры (Groq, OpenRouter) реализуют один интерфейс, но по-разному формируют заголовки
3. **Template Method** — `BaseLLMProvider` реализует общий алгоритм (fetch → retry → fallback → parse), а подклассы переопределяют детали (headers, URL)

## Ключевые механизмы

### 1. Retry (повторные попытки)

Если AI-сервис временно недоступен, мы **не показываем ошибку сразу**, а пробуем ещё раз.

```
Запрос → 429 (лимит) → ждём 1 сек → повтор → успех ✓
```

- Повторяем при: `429` (лимит запросов), `502`, `503` (сервер перегружен)
- НЕ повторяем при: `400`, `401`, `404` (это ошибки клиента, повтор не поможет)
- Задержка растёт: 1с → 2с → 4с (**exponential backoff**) — чтобы не «долбить» перегруженный сервер
- Если провайдер сам говорит «подожди 0.5 сек» через заголовок `Retry-After` — слушаемся его

### 2. Fallback (резервный провайдер)

Если после retry провайдер всё ещё не отвечает (лимит исчерпан, кончились деньги), запрос **автоматически переключается** на другого провайдера.

```
Groq (лимит) → retry → всё ещё 429 → переключение на OpenRouter → ответ ✓
```

Для пользователя это прозрачно — он просто получает ответ, не зная что модель сменилась.

Настраивается через `.env`:

```env
# Основной провайдер
LLM_JUDGE_FEEDBACK_PROVIDER=groq
LLM_JUDGE_FEEDBACK_MODEL=llama-3.3-70b-versatile

# Резервный (если Groq упал)
LLM_JUDGE_FEEDBACK_FALLBACK_PROVIDER=openrouter
LLM_JUDGE_FEEDBACK_FALLBACK_MODEL=meta-llama/llama-3.3-70b-instruct
```

### 3. SSE-парсинг (стриминг ответа)

AI не выдаёт ответ целиком — он **генерирует текст по одному слову**. Каждое слово (токен) отправляется мгновенно. Пользователь видит текст, который «печатается» в реальном времени.

```
AI отправляет:           Пользователь видит:
data: {"content":"При"}  → При
data: {"content":"вет"}  → Привет
data: {"content":" "}    → Привет
data: {"content":"мир"}  → Привет мир
data: [DONE]             → (конец)
```

### 4. Таймауты (защита от зависания)

В системе два уровня таймаутов:

**Таймаут запроса (25 сек)** — если AI-сервис вообще не отвечает (лежит, завис), запрос отменяется через 25 секунд. Это важно, потому что Supabase Edge Functions локально на бесплатном плане имеют лимит ~60 секунд на всю функцию. Judge делает два запроса (feedback + scoring), поэтому каждый должен укладываться в разумное время.

**Inactivity timeout (10 сек)** — это для стриминга. AI начал отвечать (слова приходят), но вдруг замолчал. Если нет новых данных дольше 10 секунд — соединение закрывается. Это НЕ общий таймаут: генерация может длиться 30+ секунд — это нормально. Таймер сбрасывается с каждым новым словом. Срабатывает только когда поток полностью замолчал.

```
Таймаут запроса:     [--- 25 сек ожидания ---] → отмена
Inactivity timeout:  слово...слово...[10 сек тишины]...→ отмена
```

### 5. Конфигурация через .env

Смена модели или провайдера — **одна строка** в `.env`, без изменения кода:

```env
# Сейчас: платная модель Claude через OpenRouter
LLM_CHAT_MODEL=anthropic/claude-3.5-haiku

# Переключить на бесплатную Groq:
LLM_CHAT_PROVIDER=groq
LLM_CHAT_MODEL=llama-3.3-70b-versatile
```

## Исправление бага с оценками (judge)

### Проблема

Judge использует **tool calling** — просит AI заполнить JSON-схему с оценками. Ключами в схеме были **тексты критериев на русском**:

```json
{
  "Объяснил разницу между let и const": 2,
  "Привёл примеры использования": 1
}
```

AI мог вернуть слегка изменённый текст:

```json
{
  "Объяснил различия между let и const": 2, // ← перефразировал!
  "Привёл примеры": 1 // ← сократил!
}
```

Код может искать точное совпадение ключа → не находить → ставить 0.

### Решение

Заменили текстовые ключи на **стабильные индексы**:

```json
{
  "rubric_0": 2,
  "rubric_1": 1
}
```

Текст критерия передаётся в `description` — AI видит его и знает по чему оценивать, но ключ `rubric_0` он не может перефразировать. После получения ответа индексы маппятся обратно на текст.

## Улучшения на клиенте (React)

### Отмена запросов при уходе со страницы

**Было**: пользователь уходит → запрос к AI висит в фоне → утечка памяти.

**Стало**: `AbortController` отменяет запрос при размонтировании компонента:

```typescript
useEffect(() => {
  return () => abortControllerRef.current?.abort();
}, []);
```

### Обработка ошибок скоринга

**Было**: если оценка не сохранилась — пользователь видел фидбэк, но не знал что баллы не записаны.

**Стало**: сервер отправляет маркер `[SCORING_ERROR]` в потоке → клиент показывает понятное сообщение.

### Обработка ошибок базы данных

**Было**: `.throwOnError()` мог вернуть 500 без CORS-заголовков → браузер показывал «Network Error».

**Стало**: явная проверка `{ data, error }` с корректными CORS-заголовками в ответе.

## Логирование

Теперь в логах Supabase видно всё:

```
[INFO] LLM request [stream]  { provider: "openrouter", model: "claude-3.5-haiku", messagesCount: 2 }
[INFO] LLM rate limits       { remaining: "998", limit: "1000", reset: "2m52s" }
[INFO] LLM stream connected  { connectionMs: 1269 }
[WARN] LLM switching to fallback { from: "groq/llama", to: "openrouter/llama" }
[INFO] RAG matched tasks     { count: 3, tasks: [{title: "...", similarity: 0.82}] }
```

Это помогает:

- Понять какая модель сейчас обрабатывает запросы
- Отследить rate limits и предвидеть проблемы
- Увидеть, что RAG находит релевантные задачи
- Диагностировать переключения на fallback

## Модели и стоимость

Для чата используется **Claude 3.5 Haiku** через OpenRouter — он быстрый, недорогой и хорошо работает с русским языком, что важно для естественного диалога со студентом. Для judge выбрана **LLaMA 3.3 70B** через Groq — она полностью бесплатная и достаточно точная для структурированной оценки по рубрике (tool calling с фиксированной JSON-схемой).

| Функция        | Провайдер  | Модель           | Почему                                                | Стоимость      |
| -------------- | ---------- | ---------------- | ----------------------------------------------------- | -------------- |
| Чат            | OpenRouter | Claude 3.5 Haiku | Быстрый, хороший русский, естественный диалог         | ~$0.005/запрос |
| Judge (фидбэк) | Groq       | Llama 3.3 70B    | Бесплатная, достаточна для структурированного фидбэка | бесплатно      |
| Judge (оценка) | Groq       | Llama 3.3 70B    | Бесплатная, точная для tool calling с JSON-схемой     | бесплатно      |

## Итого: что дал этот рефакторинг

| До                                     | После                                         |
| -------------------------------------- | --------------------------------------------- |
| Код дублировался в двух функциях       | Один модуль `llm-client` для всех             |
| Привязка к Groq API                    | Любой провайдер через `.env`                  |
| Сбой API = ошибка пользователю         | Retry + автоматический fallback               |
| Нет логов                              | Полное логирование запросов, ответов, лимитов |
| Оценки терялись из-за перефразирования | Стабильные ключи `rubric_0..N`                |
| Утечки стримов на клиенте              | AbortController + cleanup                     |
| Ошибки проглатывались молча            | Маркеры `[ERROR]` / `[SCORING_ERROR]` + тосты |
